# Функциональная спецификация

## 1. Концепция и принципы

Ravel — десктопный PKM-инструмент с графовой нотацией: типизированные связи, пространственная семантика, иерархическая раскладка.

**Новизна проекта — не в алгоритмах, а в композиции и философии.** Ни один из используемых приёмов (иерархическая раскладка, семантика положения, типизированные связи) сам по себе не нов. Новизна Ravel — в их сочетании под принципом «ручное управление; автоматика только советует»: пользователь осознанно строит структуру, а система не действует сама, а рекомендует (циклы, перегруженные узлы). Каждое из решений в отдельности известно, их композиция в инструменте для персональных конспектов — нет.

Принципы:

1. **Ручное управление; автоматика только советует.** Структура создаётся пользователем: решение о типе связи («это `is_a` или `has_part`?») — часть процесса понимания предметной области, поэтому каждый узел и каждая связь добавляются вручную. Система не действует сама — она рекомендует: «обнаружен цикл A → B → C → A», «у узла 12 входящих связей». Это два разных положения: первое определяет, *кто строит* структуру, второе — *как ведёт себя* автоматика.
2. **Ручная типизация** — цена за контроль. Мы её снижаем, но не отменяем: словарь мал, тип предлагается из онтологии, ошибка обратима через undo/redo.
3. **Пространственная семантика.** Положение узла несёт смысловую нагрузку (§5). Раскладка — не эстетика, а часть модели знаний.
4. **Читаемость важнее полноты.** При перегрузке карты отображается приоритетное подмножество связей; полнота не жертвуется, а прячется за явным действием пользователя (в текущем объёме — частично, см. [perspectives.md](perspectives.md)).
5. **Иерархия персональна.** Структура базы знаний отражает представления и задачи конкретного пользователя, а не предметную область «объективно». Отсюда: копирование чужой структуры противоречит смыслу Ravel, совместное редактирование — нет.

## 2. Связанные работы и позиционирование

### 2.1. Инструменты

Опыт автора с существующими инструментами:

- **Excalidraw, Miro, Coggle** — холсты и mind map. Нет типов связей, нет описаний узлов; связь — просто линия. Хороши для черновика, не для структуры.
- **Obsidian (граф связей)** — граф как побочный продукт редактора заметок. Направление и тип связи произвольны, перегруженные узлы — визуальный шум; структура не проектируется, а наблюдается.
- **TheBrain / ExcaliBrain (Obsidian)** — ручное построение сети с типизированными связями. Но фокус на локальной окрестности узла, а не на общей карте.

Близкие по духу инструменты, с которыми автор не работал, но которые важно упомянуть:

- **CmapTools (концепт-карты Новака)** — ближайший интеллектуальный предок, совпадения структурные, а не поверхностные. Связь там подписана «linking phrase», и тройка «узел — связь — узел» читается как утверждение (*пропозиция*: «мера Лебега обобщает длину интервала») — это ровно логика типизированной связи Ravel. «Общие понятия сверху, частные снизу» — базовое правило нотации; вертикальная ось Ravel — тот же принцип, закреплённый алгоритмом, а не дисциплиной рук. Перекрёстные связи (cross-links) между ветвями карты — в педагогике Новака признак глубокого понимания; в Ravel им соответствуют межленточные рёбра (§5.2). Даже «parking lot» Новака (площадка для понятий, чьё место ещё не решено) имеет прямой аналог в перспективах Ravel — инкубатор мнимых узлов ([perspectives.md](perspectives.md) §9). Принципиальная разница — **где живёт строгость нотации**: в CmapTools она держится на самодисциплине — подпись связи это свободный текст (словарь вырождается в «is / has / related to»), иерархия — правило, которое ничто не проверяет, советующей автоматики нет. В Ravel строгость перенесена в инструмент: малый типизированный словарь со свойствами (симметрия и транзитивность влияют на анализ), иерархия — ограничение алгоритма раскладки, циклы и перегруженные хабы показываются. Различие фокуса: карта CmapTools — учебный артефакт на один *focus question*, Ravel — долгоживущая персональная база знаний. Эмпирическая база концепт-карт (40+ лет исследований осмысленного обучения) — доказательство жизнеспособности ниши «структура как мышление», см. §2.2.
- **Tinderbox (Eastgate)** — двадцатилетний инструмент *spatial hypertext* (Mark Bernstein): заметки расставляются на карте вручную, и само положение осмысленно; **типизированы и узлы (прототипы), и связи (link types)**. Самая близкая точка на пересечении осей «типы + пространство» — но карта остаётся доской: алгоритмической раскладки, онтологических лент и советующей автоматики нет, автоматизация — агенты-запросы к атрибутам, не анализ структуры. macOS-only, проприетарный. Для Ravel — одновременно подтверждение жизнеспособности пространственной семантики и предупреждение: Tinderbox десятилетиями остаётся нишевым «инструментом для своих».
- **VUE (Visual Understanding Environment, Tufts)** — open-source концепт-карты для образования: узлы, подписанные связи, поддержка онтологий (OWL), семантический анализ карт. Раскладка ручная; проект заморожен с 2015 года. Для Ravel — доказательство ниши и одновременно иллюстрация главного риска академических OSS-инструментов: без постоянного мейнтейнера ниша не спасает.
- **Tana, Capacities** — типизированные *объекты* (supertags, классы): подтверждают спрос на типизацию, но структура живёт в аутлайнере/базе данных, а не в пространственной карте; связи между объектами либо нетипизированы, либо не раскладываются семантически.
- **Anytype** — типизированные объекты, и связи тоже типизированы: ребро в graph view — это link или Property reference с типом отношения. Но это система заметок, а не проектировщик структуры: граф — побочный view базы объектов, раскладка силовая и не несёт онтологической семантики, иерархической раскладки нет (лицензия source-available, не OSI).
- **Kumu** — графовый редактор для анализа сетей: силовые раскладки, метрики, кластеры. Ориентирован на анализ существующей сети, не на построение конспекта.
- **yEd (yWorks)** — бесплатный (не OSS) редактор диаграмм с эталонной автоматической раскладкой, включая иерархическую (семейство Сугиямы), и группировкой узлов. Доказывает, что раскладка сама по себе — решённая задача; но это редактор *рисунков*, а не баз знаний: связи — подписи без типов и свойств, раскладка не ограничена онтологией (лент нет), за картинкой не стоит модели знаний. Ravel отличается не «умением раскладывать», а тем, что раскладка подчинена семантике модели.
- **InfraNodus** — автоматическое извлечение графа из текста. Противоположен Ravel по философии: структура возникает без участия пользователя.
- **Heptabase** — whiteboard-based PKM: карточки на бесконечном холсте, **вложенные whiteboards** (whiteboard внутри whiteboard) — ближе всех к фрактальной идее Ravel (perspectives.md §1). Но связи между карточками нетипизированы, раскладка свободная и не несёт онтологической семантики; структура графа не является объектом проектирования.
- **Scrintal, Kosmik, Muse** — карточки на холсте, соединённые бэклинками. Связи нетипизированы, нет иерархической семантической раскладки; холст — организация заметок, а не модель дисциплины.

**Позиция Ravel.** Каждый из инструментов закрывает один аспект и проваливает остальные: холсты — свободны, но бессемантичны; ExcaliBrain и TheBrain — семантичны, но локальны или лишены онтологической раскладки; Obsidian и InfraNodus — автоматические; Anytype, Tana и Kumu — типизированы, но не про граф дисциплины; CmapTools и VUE — типизируют подписи и иерархичны по нотации, но без алгоритмической раскладки и советующей автоматики; Tinderbox типизирует и узлы, и связи и даёт осмысленное пространство, но карта там — доска без алгоритма; yEd эталонно раскладывает, но не знает семантики — это редактор рисунков. Ravel занимает промежуточную позицию: структура задаётся пользователем осознанно, типизация встроена в процесс, автоматика ограничена подсказками, раскладка семантическая. Вложенные холсты Heptabase подтверждают спрос на вложенность, но закрывают её без типизированных связей и семантической раскладки — Ravel отличается именно связкой этих трёх свойств.

### 2.2. Научные источники

- **Novak, J. D. & Cañas, A. J. «The Theory Underlying Concept Maps and How to Construct and Use Them» (IHMC Technical Report, 2008).** Концепт-карты: связь подписана linking phrase (тройка «узел — связь — узел» читается как пропозиция), иерархический принцип «общее сверху», cross-links как признак глубины понимания. Теоретическая опора — теория осмысленного обучения Ausubel: новое знание усваивается через привязку к существующей когнитивной структуре, поэтому ручное построение структуры само есть обучение, а не издержка. Для Ravel это две вещи: эмпирическое подтверждение принципа «ручное управление» (§1) сорокалетней историей применения в образовании и нотационный предок (инструмент — CmapTools, §2.1). Отличие — Ravel делает нотацию вычислимой: типы со свойствами, алгоритмическая раскладка, анализ.
- **Sugiyama, K. & Misue, K. «Visualization of Structural Information: Automatic Drawing of Compound Digraphs» (IEEE Transactions on Systems, Man, and Cybernetics, 1991).** Классическая работа по иерархической раскладке ориентированных графов; вводит *compound digraphs* — вложенные (иерархические) графы, где узел может содержать подграф. Это теоретическая база раскладки Ravel (§5) и, в перспективе, фрактальной вложенности карт ([perspectives.md](perspectives.md) §1).
- **Heer, J. & Shneiderman, B. «Interactive Dynamics for Visual Analysis» (Queue, 2012)** и работы по *semantic substrates* (Shneiderman & Aris, 2006): идея, что зоны разметки (substrates) с заданной семантикой — «сначала раздели, потом покажи связи» — повышает читаемость больших сетей. Ravel применяет этот принцип на уровне *лент* внутри слоя раскладки (§5): узлы группируются по семантическому классу, и упорядочивание идёт внутри групп.
- **Gärdenfors, P. «Conceptual Spaces: The Geometry of Thought» (MIT Press, 2000).** Концептуальные пространства: понятия представлены как области в многомерных пространствах качеств, а не только символами или ассоциациями. Пространственная семантика Ravel — прагматичная проекция этой идеи: две оси карты (иерархия, онтологический класс) заданы онтологией и несут смысл, а не выбраны произвольно.
- **Luhmann, N. «Kommunikation mit Zettelkästen» (1981; в сб. «Öffentliche Meinung und sozialer Wandel», Westdeutscher Verlag).** Первичное описание метода: заметка-атом, связи вместо папок, «нет привилегированных мест», ветвление вместо тематической иерархии. Методологический предок Ravel; разбор соответствия и разрывов — §2.4.
- **Ahrens, S. «How to Take Smart Notes» (2017, 2-е изд. 2022).** Современная сводка принципов цеттелькастена (атомарность, объясняй связи, fleeting vs permanent notes) и их педагогическое обоснование. Источник списка принципов для §2.4.

### 2.3. Отличие от источников: тезис об ограничениях плоской карты

Тезис Ravel: одна плоская карта неизбежно проигрывает по двум независимым направлениям, и оба закрываются не алгоритмом раскладки, а структурой инструмента:

1. **Глубина.** Карта не может показать внутреннюю структуру понятия, не превращаясь в кашу. Ответ — вложенность: фрактальная нотация (perspectives.md §1), теоретическая база — compound digraphs Sugiyama–Misue; спрос на вложенность подтверждают вложенные whiteboards Heptabase — но без типизированных связей и семантической раскладки.
2. **Альтернативная иерархия.** Карта не может показать два равноправных способа упорядочить одни и те же понятия (по `is_a` и по `has_part`). Ответ — призрачные альтернативы (perspectives.md §2): смена проекции одних и тех же данных, а не их копия.
3. Третье **наблюдение** — не ограничение плоской карты, а её типичное следствие: свободные визуальные каналы (цвет, форма, стиль линии) используются как украшение, а не как информация. Причина не в пользователях: на свободном холсте значение цвета ничем не закреплено — словарь держится на самодисциплине (та же ситуация, что со строгостью нотации в CmapTools, §2.1), поэтому инвестировать в него рационально не хочется. Вывод для Ravel: семантические каналы должны быть выведены из модели, а не назначены вручную. Цвет и стиль узла и связи — свойства типа онтологии (§4): пользователь решает о типе, визуальный канал следует бесплатно. Цвет становится надёжным носителем именно потому, что его нельзя нарушить.

Далее, по каждому направлению источники дают части: Sugiyama–Misue — раскладку и основу вложенности; semantic substrates — принцип «сначала раздели на смысловые зоны, потом покажи связи», реализованный в онтологических лентах (§5.2); conceptual spaces — рамку «карта как проекция смыслового пространства» (прагматичная проекция идеи Gärdenfors, а не формальная теория — честные границы этой опоры см. в §5.1); Novak–Cañas — нотацию связей-пропозиций и педагогическое обоснование того, что ручное построение структуры само есть обучение (§2.2). Ravel компонует эти части вокруг тезиса: разные механизмы для разных ограничений, а не один «красивый» алгоритм.

### 2.4. Соответствие методу Цеттелькастен

Цеттелькастен (метод Лумана; сводка принципов по Аренсу и форумным
обсуждениям) — ближайший методологический родственник Ravel. Разбор по
принципам, с честными разрывами.

**Совпадения и усиления:**

- **Атомарность — с оговоркой.** Узел Ravel — один концепт (одна функция, одна
  теорема): структурная атомарность; классика сама предупреждает, что
  атомарность — «не жёсткий закон, а компас». Оговорка: атом цеттеля —
  идея/утверждение, атом Ravel — понятие; идеи-утверждения живут на рёбрах
  (тип + description, §4.2) — это пропозициональная логика концепт-карт
  Новака (§2.1). Оба вида атомов покрыты; «винегрет» в description остаётся
  дисциплиной пользователя, системой не проверяется.
- **Связи — усилены.** Связь обязательна и типизирована; форумное «связи
  усиливают заметку» и «одинокая заметка = потерянная» получают механику:
  хабы, циклы, тень — система буквально не даёт заметке потеряться (advisors).
  Тип со свойствами (симметрия, транзитивность) — данные связанных заметок,
  вбираемые в анализ (§5.3).
- **Объясняй связи — встроено в модель.** Description ребра «почему существует
  эта связь» (§4.2) — first-class поле, не конвенция.
- **Не беспокойся о структуре хранения — совпадение полное.** Плоский граф,
  позиции вне идентичности (ADR-003), папок нет: принципу «нет привилегированных
  мест» удовлетворено строже, чем в инструментах с папками. Фрактальные карты
  (persp. §1) — электронный аналог ветвления Лумана: карта = «папка» ≤ 10³
  узлов, но со связями через границу, чего папки не дают.
- **Карта для темы — это нотация Ravel.** Каждая карта — structure note, только
  не список ссылок, а пространственный граф; классический принцип выполнен в
  гипертрофированной форме.

**Честные разрывы:**

- **«Не удаляй устаревшие заметки».** Каскадное удаление (ADR-002) существует
  ради undo внутри сессии и нормализуется при save/load; архива и типа связи
  `superseded_by` нет. Для цеттель-дициплины это заметный разрыв: история
  развития мысли не сохраняется. Минимальный фикс в текущей модели — связь
  `superseded_by` + уход в «сумерки» вместо физического удаления (жест advisors
  существует, архива пока нет).
- **Ссылки на источники.** Поля источника ни у узла, ни у ребра нет; для
  научного конспекта это принципиально. Закрывается полем источника
  (persp. §17) — перспектива, не MVP.
- **«Накидывай без страха» — пока не закрыт.** Обязательный тип связи и диалоги
  делают цену входа выше, чем у fleeting notes. Инкубатор (persp. §9) —
  запланированное закрытие: слой мнимых узлов — это fleeting notes в терминах
  Аренса.

**Философский разрыв (не дефект).** Луман был против систематической
тематической иерархии как принципа хранения, а Ravel — её апофеоз: вертикаль
кодирует иерархию, горизонталь — онтологию. Но «против тематики» у Лумана было
средством против ограничения мысли чужими рамками; позиция Ravel «иерархия
персональна, структура отражает задачу» (§1, принцип 5) — тот же тезис,
доведённый до предела: иерархия не от предметной области, а от пользователя.
Здесь Ravel не нарушает цеттель, а спорит с ним на его же поле.

**Маппинг (рецепт следования методу в Ravel):** концепт → узел;
утверждение/идея → ребро с description; structure note → карта; fleeting note →
мнимый узел инкубатора (когда появится); иерархия Лумана → фрактальные карты
с портами-алиасами.

**Вывод.** Следовать Цеттелькастену в Ravel можно, и по ряду принципов —
проще, чем в большинстве инструментов. Для полного закрытия метода не хватает
трёх вещей, и все три уже описаны в перспективах: (1) поле источника
(persp. §17), (2) «сумеречный» архив вместо удаления (жест advisors + связь
`superseded_by`), (3) инкубатор (persp. §9). Цеттелькастен-совместимость — не
новая фича, а маркировка уже запланированного.

## 3. Область применения и не-цели

Аудитория: любой исследователь, строящий конспект по области со сложной
системой понятий. Пространственная семантика (§5) полностью раскрывается, когда область допускает одновременно два условия:

1. малый типизированный словарь связей — типизация осмыслена и не раздувает
   онтологию (стоимость словаря — §4.1);
2. иерархичность — понятия области поддаются упорядочиванию от общего к
   частному, так что вертикальная ось карты несёт смысл, а не назначается
   искусственно. Какая именно иерархия доминирует — решение пользователя,
   а не свойство области (принцип 5, §1).

Области, богатые обеими структурами (таксономии, иерархии теорем, нормативные
системы, родословные вводных курсов), получают семантическую раскладку почти
бесплатно. В областях с преимущественно плоской, нарративной или ассоциативной
структурой знания инструмент не ломается, но семантические оси несут меньше
смысла, и честная граница Ravel проходит здесь, а не по списку дисциплин.

**Не-цели** (сознательно за пределами проекта):

- автоматическое построение графа: извлечение связей из текста (NLP), автоматические связи — структура только ручная. LLM допустимы лишь как опциональные рекомендации в далёкой перспективе (link prediction по окрестности узла), никогда как автоматическое действие и не как извлечение из текста;
- коллективная работа, синхронизация, облако — локальное однопользовательское приложение;
- замена системы заметок (Obsidian и т. п.) — компаньон для проектирования структуры, а не хранилище контента;
- раскладка «красиво любой ценой» — раскладка семантическая и управляемая пользователем.

## 4. Модель данных

### 4.1. Стоимость ручной типизации

Каждая новая связь требует решения о типе. Это цена за контроль над структурой: понять дисциплину через двадцать типов невозможно, через пять — можно. Ravel снижает цену, не отказываясь от решения: словарь мал и расширяется осознанно (§4.5), тип предлагается из онтологии концов (§4.4), а ошибка обратима через undo/redo. Тип обязателен в момент создания связи: связь без типа — не связь в модели Ravel.

**Снижение стоимости типизации.** Ручная типизация не должна прерывать поток мысли. Три механизма снижают цену решения, не отменяя его: (1) *липкий тип* — последний использованный тип связи становится типом по умолчанию для следующего создания; пользователь может подтвердить его одним Enter, не открывая полный диалог; (2) горячие клавиши для 3–4 наиболее частых типов (`I` — is_a, `H` — has_part, `D` — is_defined_on, `M` — is_model_of); (3) контекстное предложение — диалог открывается с уже выбранным типом по онтологии концов (§4.4), так что в типичном случае пользователь подтверждает предложенное. Все три механизма — не автоматизация, а снижение трения; решение о типе остаётся за пользователем: липкий тип и горячие клавиши ускоряют ввод, а не заменяют решение. Текущий липкий тип всегда виден в UI (индикатор в статус-баре и метка при протяжке связи), чтобы подтверждение Enter никогда не было слепым. В план roadmap (недели 1–12) эти механизмы не входят: ближайший потребитель — полировка после вехи «свой конспект» ([roadmap.md](roadmap.md), хвост документа).

### 4.2. Сущности и идентификаторы

- **Узел**: `id`, название, описание, тип (`model`, `function`, `theorem`, `method`, …).
- **Размер узла** — безразмерный множитель масштаба (`double`; 1 = базовый размер типа, диапазон UI 0.5–5.0): абсолютные пиксели в модель не входят, умножатель задаётся пользователем вручную.
- **Позиция узла** — не часть идентичности узла (ADR-003): хранится в `Graph` отдельным вектором `positions_`, в файле — секцией `positions` (§4.3); ручная позиция имеет приоритет над раскладкой (§5.5).
- **Связь (ребро)**: `id`, `from`, `to`, тип связи, опционально описание — короткое пояснение, *зачем* существует эта связь (почему выбран именно такой тип, в каком смысле узлы связаны). Описание не влияет на отрисовку, раскладку и анализ; оно для человека, возвращающегося к карте через месяц.
- **Тип связи** — именованная сущность со свойствами: цвет, стиль стрелки, флаги `symmetric` и `transitive`. Встроенный словарь (`is_a`, `has_part`, `is_model_of`, `is_defined_on`, …) расширяем (§4.5). Свойства типа влияют на отрисовку и раскладку (§5).
- **Тип узла** — именованная сущность со свойствами: цвет, форма (`shape`), цвет рамки (`frame_color`). Хранится в словаре `node_types` (§4.3); цвет, форма и рамка узла определяются его типом (R8: имя типа — только ключ словаря). Допустимые значения `shape`: `rect`, `oval`, `rounded_rect` (2026-10-24; валидация — `IsValidShape`).
- `id` у рёбер введён осознанно: нужен для undo/redo (команды ссылаются на удалённые связи) и будущих ссылок из фрактальных нотаций ([perspectives.md](perspectives.md)).

**Идентификаторы.** Целые (`uint64_t`), выдаются монотонными счётчиками `next_id_node` и `next_id_relation`, хранимыми в файле — по одному на вид сущностей. Не переиспользуются после удаления — это нужно для корректной работы undo/redo. При ручном редактировании JSON новый id должен быть больше максимального существующего среди сущностей своего вида.

> **ADR-001 (2026-09-21): раздельные счётчики id для узлов и рёбер.** Единый счётчик `next_id` на оба вида сущностей заменён двумя: коллизия, которую лечит общее пространство id (узел против ребра), на практике не случается, а раздельные счётчики делают правила генерации и валидации независимыми и проще. Последствие — несовместимое изменение формата: `format_version` 1 → 2 (§4.3). Полный текст решения — [adr/ADR-001-id-generation.md](adr/ADR-001-id-generation.md); детали реализации и отвергнутые альтернативы — [implementation.md](implementation.md), R1.

**Валидация счётчиков при загрузке.** Проверку выполняет ядро, не загрузчик: `Graph::FromSnapshot` отклоняет снапшот, если `next_id_node` не строго больше максимального id узлов, а `next_id_relation` — максимального id рёбер. Если условие нарушено, загрузка завершается ошибкой с указанием счётчика, его значения и максимального существующего id — «исправьте файл вручную». Молчаливая починка (автоматическое повышение счётчика) запрещена: это скрывает ошибку в данных и может привести к коллизии с id, сохранённым в стёртой записи undo-лога и вернувшимся при откате. Пользователь обязан исправить файл.

**Вставка между файлами.** При копировании узла (или группы узлов) из одного файла в другой все скопированные сущности получают новые id из счётчиков целевого файла. Оригинальные id не сохраняются: они могли бы конфликтовать с существующими id целевого файла. Связи между скопированными узлами сохраняются (перенаправляются на новые id); связи с узлами, не попавшими в копию, отбрасываются. Это осознанное решение: id — локальный идентификатор в рамках файла, а не глобальный.

Цвет узла определяется его типом; цвет и стиль стрелки — типом связи.

### 4.3. Формат файла

Хранение — JSON (человекочитаемый формат, удобен для отладки и версионирования в git). Поле `format_version` обязательно; при несовместимом изменении схемы версия увеличивается (прецеденты: ADR-001 — 1 → 2, раздельные счётчики; ADR-003 — 2 → 3, секция `positions`; текущая версия — 3). Обратную совместимость загрузчик поддерживать **не обязан**: до первого публичного релиза формат не стабилен, старые файлы ломаются намеренно (в рамках курсовой миграция не требуется). Обязательность чтения предыдущей версии вводится вместе с первым релизом — как контракт, а не как надежда.

**Поля `size` и `description` (2026-10-03; уточнено 2026-10-19).** Опускаются при записи, если равны умолчанию (`size = 1`, пустое описание): файл не раздувается значениями по умолчанию, Load подставляет умолчания. Секция `positions`, напротив, пишется всегда и целиком: незаданная позиция записывается как `null` — i-й элемент `positions` обязан соответствовать i-му элементу `nodes` (ADR-003).

**Пометка «допустимый цикл».** Циклы, помеченные пользователем как допустимые (§5.4), хранятся в поле `allowed_cycles` — списке наборов id рёбер, образующих цикл. При загрузке эти циклы исключаются из предупреждений.

**Семантика поля `allowed_cycles` (закрыто 2026-11-02; заменяет статус «зарезервировано» от 2026-10-03).** Поле хранит циклы, помеченные пользователем как допустимые (§5.4), — список наборов id рёбер. Save пишет поле всегда; Load требует секцию (массив массивов id рёбер, иначе `runtime_error`) и отдаёт её вместе со снапшотом (`FileDoc`); содержимое round-trip'ится без потерь. Версия формата осталась 3: обратная совместимость до первого релиза не поддерживается (см. вводный абзац §4.3), файлы без поля отклоняются — все примеры пересохранены.

**ADR-003.** `positions` — ручная позиция узла (`struct Position { double x; double y; }`), задаваемая пользователем поверх раскладки (spec §4.2); объект `{"x", "y"}` или позиция не задана вручную: JSON null; i-й элемент positions соответствует i-му элементу nodes

### 4.4. Добавление узлов и связей

- **Узел.** Двойной клик по пустому месту сцены создаёт узел и открывает диалог ввода названия и выбора типа; тип по умолчанию — `model`. Альтернатива — горячая клавиша `N` в позиции курсора. Горячие клавиши регистрируются в обеих раскладках: в русской `QKeyEvent` отдаёт кириллические символы, поэтому используются физические клавиши (`key()` без текста / кириллические алиасы), иначе `I`/`H`/`D`/`M` молча не сработали бы.
- **Связь.** Основной способ — протяжка с зажатым Ctrl (Ctrl+drag) от узла-источника к узлу-цели: источник помечается как `from`, цель — как `to`. При отпускании открывается диалог выбора типа связи. Направление протяжки задаёт `from`/`to`; для симметричных типов направление несущественно и отрисовывается двусторонней стрелкой. Снижение трения типизации — липкий тип с индикатором в статус-баре, горячие клавиши `I`/`H`/`D`/`M` для частых типов, предложение типа по онтологии концов в диалоге (для пары function → model — `is_defined_on`) — **в плане**: в недели 1–12 не входит, ближайший потребитель — полировка после вехи «свой конспект» (§4.1).
- **Создание узла сразу со связями.** Альтернатива протяжке для сценария «добавить узел вместе со всеми его связями»: в диалоге создания узла построчно вводятся соседние узлы и типы связей, например `Степенная функция is_defined_on Вещественная прямая`. Конвенция направления — та же, что для протяжки: **порядок слов = `from` → `to`**. Новый узел может стоять в строке слева (тогда он будет `from`) или справа (`to`); позиция имени нового узла в строке определяет его роль. Соседний узел ищется по имени среди существующих; если не найден, строка помечается ошибкой в диалоге до подтверждения — молчаливое создание соседа не допускается (структура ручная, принцип 1). Тип связи вводится именем из словаря. Создание узла вместе со всеми его рёбрами оформляется **одной командой** undo/redo: откат убирает и узел, и все его связи разом - **в плане**.
- **Смена типа.** Двойной клик по ребру открывает тот же диалог; изменение оформляется командой и доступно через undo/redo.
- **Удаление.** Выделение + `Delete` или `Ctrl+D` (rubber-band). Удаление узла каскадно удаляет его рёбра; команда сохраняет их для отката. Контекстное меню — в перспективах.

Тип обязателен в момент создания: связь без типа не создаётся. Это осознанное ограничение: тип — часть модели понимания, а не метаданные.

### 4.5. Пользовательские типы связей

В текущем объёме встроенный словарь типов фиксирован и покрывает основной фокус (§3). Добавление нового типа — ручное редактирование секции `relation_types` в JSON-файле (§4.3): пользователь указывает имя, цвет, стиль стрелки, флаги `symmetric` и `transitive`. После перезагрузки файла тип становится доступен в диалогах создания и редактирования связей, участвует в отрисовке и (кроме симметричных, см. [perspectives.md](perspectives.md)) в раскладке.

**Удаление типа из `relation_types`.** Если пользователь удаляет запись типа из `relation_types`, но рёбра с этим типом остаются в файле, загрузка завершается ошибкой с сообщением «тип связи "X" отсутствует в relation_types, но используется рёбрами N, M — добавьте тип обратно или удалите рёбра». Это согласуется с инвариантом «тип каждой связи должен существовать в словаре» (architecture.md §4). Альтернатива — автоматическое удаление рёбер — недопустима: это молчаливая потеря данных (без диалога пользователь не поймёт, почему связь исчезла).

UI-редактор словаря — в перспективах. В текущем объёме инструмент рассчитан на фиксированную онтологию с точечными ручными расширениями: это осознанный компромисс, а не временное ограничение.

**Неизменяемость записей словаря.** Запись типа после создания не меняется через UI: ни перекраски, ни правки флагов — только удаление и создание заново (посредством редактирования JSON, §4.3). Это осознанное решение, а не недоработка инструмента. У автора есть прямой опыт «настройки вместо структуры» в ExcaliBrain: свободная косметика оттягивает от смысловой нагрузки карты (принцип 4, §1), а медленный путь правки JSON делает изменение цвета осознанным актом, а не дудлингом. Следствие: переименование типа невозможно — создаётся новый тип, а узлы со старым именем продолжают ссылаться на старую запись (правило удаления типа выше применяется к старой записи). Расширение свободы настройки (перекраска, цвет текста, правка флагов через UI, undo для словаря) отложено как отдельный вопрос: ближайший UI-редактор словаря в перспективах — только создание типов (perspectives.md §6).

## 5. Семантическая раскладка

> Единый раздел вместо бывших §4 «Пространственная семантика» и §5 «Иерархическая раскладка»: они описывали один алгоритм с разных сторон и конфликтовали. Договорённость: **вертикаль — зона ответственности Сугиямы, горизонталь — онтологическая ось.**

### 5.1. Две оси карты

- **Вертикаль — иерархия (алгоритм Сугияма).** Общие понятия сверху, частные снизу; направленные рёбра идут сверху вниз. Собственная реализация по Sugiyama & Misue (§2.2): топологическая слоистость → минимизация пересечений методом барицентров → назначение координат. Иерархические типы (`is_a`, `has_part`, …) задают слои.
- **Горизонталь — онтологическая ось.** Каждый слой делится на **ленты** — подпоследовательности узлов одного семантического класса (типа узла). Порядок лент в слое фиксирован и задаётся онтологией (например: теоремы / методы / функции / модели слева направо). Это приложение принципа semantic substrates (§2.2): сначала разделение на смысловые зоны, потом упорядочивание внутри них.

### 5.2. Барицентры с ограничением на ленты

На этапе минимизации пересечений запрещены перестановки, нарушающие принадлежность к ленте:

- пересчёт позиций и подсчёт пересечений выполняются **внутри каждой ленты** (метод барицентров, итерации по слоям);
- порядок лент внутри слоя не меняется алгоритмом — он задан онтологией;
- при равных барицентрах порядок узлов внутри ленты определяется id: раскладка детерминирована, и тесты на пересечения не зависят от порядка обхода контейнеров;
- ленты, не содержащие узлов в данном слое, схлопываются и места не занимают: порядок лент фиксирован, но присутствуют только непустые;
- Рёбра между узлами разных лент (например, `is_defined_on` из function-ленты в model-ленту) не оптимизируются: их горизонтальные пересечения неизбежны при фиксированном семантическом порядке. Они не устраняются раскладкой, но визуально смягчаются в MVP: fading по числу пересечений и hover-подсветка (см. roadmap.md, этап 3c). В перспективе — слияние параллельных рёбер в общий путь и hierarchical edge bundling (perspectives.md §6).

Так семантическая ось перестаёт быть «постпроцессингом поверх раскладки» и становится ограничением самого алгоритма — конфликта между семантикой и минимизацией пересечений не возникает: оптимизируется ровно то, что семантикой не зафиксировано.

### 5.3. Свойства типов связи

- Иерархические типы (`is_a`, `has_part`, …) задают слои (§5.1).
- Транзитивные типы не порождают дополнительные рёбра в модели, но учитываются анализом графа (§6).
- Симметричные типы (`isomorphic_to`, …) иерархии не создают; их горизонтальная отрисовка внутри одного слоя — **не входит в базовую раскладку**, вынесена в перспективы ([perspectives.md](perspectives.md) §6).

### 5.4. Циклы

Обнаружение циклов идёт **вровень с раскладкой**, а не отдельным постфактум-анализом: перед слоистостью выполняется DFS; обратные рёбра (замыкающие цикл) не участвуют в назначении слоёв, визуально выделяются (пунктир/цвет) и сопровождаются советом, а не предупреждением: слой advisors показывает цикл как вопрос («здесь цикл: создать связь или сменить тип?»), клик по светлячку открывает диалог «пометить цикл как допустимым?» (кнопка «Нет» — по умолчанию: пометка необратима до удаления рёбер); при подтверждении цикл записывается в `allowed_cycles` (§4.3) и совет гаснет. Совет ничего не решает сам — действие выполняет пользователь; грамматика советов зафиксирована в [advisors.md](advisors.md). Помеченный цикл советом не сопровождается. Алгоритм раскладки остаётся корректным на циклических графах за счёт стандартного приёма разрыва циклов. Детекция циклов имеет двух разных потребителей: раскладку (этот параграф — DFS разрывает обратные рёбра для слоистости) и read-only совет по подграфам одного типа связи, при этом симметричные типы исключены из детекции вовсе (implementation.md R20: цикл в графе симметричных связей — не аномалия, подсказка «иерархия петлит» для них бессмысленна; совет-вопрос ≠ разрыв цикла для слоистости — это не одна фича, а два потребителя одного анализа).

### 5.5. Ручные переопределения

Пользователь может переопределить позицию узла вручную; ручное размещение имеет приоритет над алгоритмическим и сохраняется в файле. Кнопка «Разложить» пересчитывает только автоматические позиции.

## 6. Анализ графа

- **Обнаружение циклов (DFS)** — интегрировано в раскладку (§5.4): совет-вопрос слоя advisors ([advisors.md](advisors.md)); пометка «допустимый цикл» — ручная.
- **Полуавтоматический размер узла** пропорционален степени (входящая + исходящая); ручное задание возможно. В roadmap (недели 1–12) не входит — ближайшая полировка после вехи «свой конспект»; PageRank — в перспективах ([perspectives.md](perspectives.md) §6).
- При числе связей узла более N отображаются приоритетные, остальные — по запросу. Реализация топ-N отображения — в перспективах; в текущем объёме перегруженный узел выделяется визуально (тень хаба, [advisors.md](advisors.md)), без вердиктов.

## 7. Ограничения

- не предназначен для баз знаний > 10³ узлов;
- нет синхронизации, облака, коллективной работы;
- нет импорта из Obsidian / Coggle / Miro;
- формат JSON не совместим с другими инструментами;
- в MVP пользовательские типы связей задаются редактированием JSON.

## 8. Проектируемые возможности

Отдалённые перспективы (фрактальная вложенность, призрачные альтернативы иерархии, алиасы, симметричные рёбра в раскладке, PageRank и др.) вынесены в отдельный документ: [perspectives.md](perspectives.md). Они описывают направление развития и **не входят в текущий объём курсовой работы**.
