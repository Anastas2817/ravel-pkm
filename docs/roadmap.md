# Дорожная карта (MVP курсовой работы)

## Цель проекта (SMART)

**К защите курсовой (неделя 12 плана, декабрь 2026) выпустить работоспособный MVP Ravel — десктопное приложение для ручного проектирования баз знаний с типизированными связями и иерархической раскладкой, в котором пользователь с помощью канваса создаёт граф из ≥ 20 узлов и ≥ 30 связей, сохраняет и загружает его в git-friendly JSON без потерь (round-trip подтверждён автотестом), раскладывает граф автоматически с меньшим числом пересечений, чем у наивной слоистой раскладки (на тестовом графе из 20 узлов; при провале основного плана — по лестнице деградации F2/F3, раздел «Риски»), и отменяет/повторяет любое действие через команды (undo/redo); покрытие тестами ядра ≥ 70 % строк (gcovr; в CI — гейт по строкам), CI зелёный на момент защиты.**

Раскладка по критериям:

| Критерий | Обоснование |
|---|---|
| **S** (конкретная) | Один сценарий сквозь весь стек, а не набор фич: канвас → типизированный граф → JSON → раскладка → undo/redo. Перечисленные фичи — это этапы 2–4 плана ниже, ничего сверх плана в цель не входит |
| **M** (измеримая) | Каждый критерий имеет число и способ проверки: ≥ 20 узлов/≥ 30 связей (демо-база), round-trip-автотест, счётчик пересечений < наивной раскладки, покрытие ≥ 70 % (gcovr), CI-бейдж. Источник истины — таблица «Метрики успеха» ниже; цель её не дублирует, а собирает |
| **A** (достижимая) | Нагрузка 2–3,5 ч/день × 12 недель; недели 1–4 уже закрыты на момент фиксации цели; неделя 12 — буфер; раскладка привязана к лестнице деградации F1→F3, то есть цель достижима и при провале самой рискованной фазы (этапы 3a/3b) |
| **R** (значимая) | Результат — работающий продукт, реализующий спецификацию spec.md §1 (типизированные связи, семантическая раскладка, ручное управление), а не прототип одной фичи; демонстрабелен на защите без оговорок |
| **T** (ограниченная во времени) | Горизонт — 12 недель, жёсткая точка — неделя 12 (дата защиты); промежуточные контрольные точки — конец каждой недели (показываемое состояние) и конец недели 8 (критерий перехода на запасной план) |

**Горизонт: 12 недель, нагрузка 2–3,5 часа в день.** План намеренно аскетичен: это объём, который выполним без выгорания, — а проект автор продолжит вне курсовой, поэтому всё «мечтательное» уехало в [perspectives.md](perspectives.md) и в хвост.

Каждая неделя заканчивается работающим состоянием, которое можно показать. Буферы заложены явно.

## Метрики успеха (MVP)

| Метрика | Цель | Как измеряется |
|---|---|---|
| Round-trip save → load → save | семантическое совпадение: те же узлы, рёбра, типы, счётчики `next_id_*`; порядок ключей и элементов не важен | автотест сравнивает нормализованные структуры (парсинг обоих JSON и глубокое сравнение, а не байтовое) |
| Пересечения рёбер на тестовом графе (20 узлов) | меньше, чем у наивной слоистой раскладки | счётчик пересечений |
| Покрытие тестами ядра | ≥ 70 % строк к защите (контроль недели 11 — ≥ 50 %) | gcovr (CI-гейт по строкам) |
| CI | зелёный пайплайн на момент защиты, каждое красное состояние в истории main закрыто фикс-коммитом | GitHub Actions |

*(Бенчмарки на 10²–10³ узлов убраны из MVP — лимит проекта 10³ узлов, а измерения производительности вынесены в перспективы.)*

## Риски и запасные планы

**Главный технический риск проекта — модифицированный Sugiyama с онтологическими лентами (этапы 3a/3b).** Это осознанно самая трудная часть: ограничение на ленты нестандартно, а назначение координат с этим ограничением (блоки выравнивания не пересекают границы лент) — самая сложная фаза классического алгоритма. Риск принят, и для него есть план деградации: **провал раскладки ≠ провал проекта** — каждая ступень ниже это работающий, показываемый результат.

**Критерий перехода на запасной план (конец недели 8).** Переходим на F2, если выполнено хотя бы одно: (а) 3b не работает на тестовых графах ≤ 20 узлов; (б) пересечений на тестовом графе не меньше, чем у наивной раскладки; (в) 3b съедает буфер недели 8 и угрожает этапу 4. Решение фиксируется в репозитории (коммит + заметка в README) — откат на F1 после перехода не планируется.

**Лестница деградации:**

- **F1 (основной план).** Полный Sugiyama: слоистость → барицентры внутри лент → координаты с блоками выравнивания внутри лент (этапы 3a, 3b).
- **F2 (запасной).** Классический Sugiyama без жёсткого ограничения на ленты: барицентры свободны, принадлежность к ленте учитывается как мягкий приоритет (стабильная сортировка по (лента, барицентр)). Метрика «пересечений меньше, чем у наивной раскладки» при этом сохраняется.
- **F3 (гарантированный минимум).** Наивная слоистая раскладка: слои по longest-path, порядок внутри слоя — по классу и id. Без оптимизации пересечений, но с честной семантической вертикалью (общее сверху) и детерминированностью.
- **Во всех вариантах.** Ручное переопределение позиций (spec.md §5.5): карта остаётся полезной даже без автоматической раскладки.

**Что не зависит от успеха раскладки.** Цикл-детекция, цветовое кодирование, undo/redo, JSON, канвас делаются в любом сценарии — провал 3b отрезает только «красивую» часть, не ядро.

**Второй риск — неделя 9 превратится в рефакторинг.** Если недели 4–5 писать канвас с прямым доступом к `Graph`, неделя 9 (команды) потребует переписать весь UI. Митигация: все действия канваса с первого дня оформляются командами (пока без стеков undo/redo) — тогда неделя 9 добавляет только стеки.

**Порядок жертв при нехватке времени (по убыванию безболезненности).** Этап 3c (fading — косметика) → часть полировки цветов → объём Doxygen (оставить док-комментарии только к публичному API ядра). Никогда не режем: тесты инвариантов, round-trip, undo/redo.

## Известные направления (фиксация, не текущий план)

Решения, обоснования которых созрели, но потребители ещё не появились — чтобы развилка не переоткрывалась. Правило 1 применено к самому языку: стандарт и структуры меняются по запросу потребителя, не забегая вперёд.

- **DomainError (запрос — неделя 9).** Маленький `DomainError : std::logic_error` для отличения битых вызовов App/undo от прочих `logic_error`. Тонкость: различение «битый файл vs битый вызов» уже существует — файловые сбои кидают `runtime_error`, вызовы — потомков `logic_error`; не хватает только гранулярности внутри вторых. Делается по запросу недели 9.
- **StorageError.** `enum class StorageErrorCategory { Parse, FormatVersion, Validation, Io }` + один тип исключения с `category()`, `what()` и опциональной цепочкой причин — вместо различения сбоев парсингом строки `what()` (заведомо хрупкая связь). Реализовать вместе с UI-реакциями на ошибки (например, «файл не найден» → предложить создать новую базу), иначе dead code.
- **Модули валидации V1–V6 + `validation.hpp` (2026-10-17, разбор).** Сводка дублей: V1 доменные строки (цвет/форма/стрелка), V2 геометрия узла (`size > 0 && isfinite`, позиция finite), V3 концы ребра (тип в онтологии, `from`/`to` живы), V4 уникальность имён типов, V5 счётчики, V6 id и связность снапшота. Целевая философия — B: `Node`/`Relation`/`*Type` как DTO-агрегаты (пользовательские конструкторы убраны), вся валидация — свободные `Validate*`, возвращающие `ValidationError`/`vector<ValidationError>`; битый вызов → исключение (`logic_error`), битые данные файла → накопление за один проход (`expected`). Живое доказательство необходимости именованных хелперов: рассинхрон «`AddNode` проверяет `size <= 0`, конструктор — ещё и `isfinite`» (правило 28, уточнение 2026-10-17). Отдельный `core/include/validation.hpp` вводится **вместе** со вторым потребителем — expected-переходом `JsonStorage::Load` (тогда storage включает 20-строчный хедер вместо всего `graph.hpp`; правило 31: модуль вместе с потребителем, не «потому что сводка красивая»). Заодно чинится баг: `Load` ловит `json::exception`, а битое доменное значение из конструктора улетает наружу `invalid_argument`, ломая контракт «файл → `runtime_error`».
- **C++23 + std::expected + накопление ошибок валидации снапшота (связанная пара).** Формат — git-friendly JSON, который правят руками и получают после merge-конфликтов; fail-fast по первому нарушению инварианта заставляет править файл итерациями («исправил id → перезапустил → следующая ошибка»). Валидация, возвращающая `std::vector<ValidationError>` за один проход, — реальное UX-улучшение именно этого сценария; `std::expected` делает дизайн естественным (накопление через исключения по природе неудобно). Заметка: накопление не требует `expected` в принципе (`Validate() -> vector<ValidationError>`, `FromSnapshot` бросает при непустом), C++23 делает его элегантнее, не возможнее. Решение о переходе на C++23 принято раньше этого пункта (2026-10-13: `std::expected`, concepts инициатив, `contains`), поэтому на момент реализации остаётся только сам переход storage на `expected`.

## После курсовой: веха «свой конспект»

Критерий того, что проект жив и нужен: к концу учебного года — собственный конспект на 100+ узлов, который ведётся в Ravel, а не в Coggle/Excalidraw. Эта веха важнее любых внешних метрик (звёзды, пользователи): совпадение автора и пользователя — главный двигатель проекта. До достижения вехи новые фичи из perspectives.md не начинаются.

**Первые фичи после вехи** (до мечтательного из perspectives.md): **автосейв** — таймер в App, тот же путь сохранения, что у Ctrl+S, наблюдатель модели не нужен (architecture.md §2.3); **поиск по титулам** — линейный проход по модели на запрос из UI через App, индекс для 10³ узлов не нужен.
